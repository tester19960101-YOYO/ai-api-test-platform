## 当前阶段说明

当前项目已完成到第 10.2 阶段，当前已实现 Pytest + Requests 基础执行引擎，并完成断言系统2.0融合引擎和 DSL 可视化断言系统，当前断言体系以 DSL 为用户侧表达语言。

当前执行引擎能力是 当前基础闭环：

- 从数据库读取项目、环境、接口资产和测试用例

- 使用 pytest-html 生成 HTML 报告
- 保存执行任务、执行结果和测试报告元信息

## 请求能力

- GET
- POST
- PUT
- DELETE
- PATCH
- base_url
- headers
- query params
- JSON body
- timeout
- retry_count
- 环境公共 headers
- 环境级 token / cookie / 自定义鉴权 headers

请求头合并优先级：

```text

```

如果环境 Cookie 和用例 Cookie 同时存在，会合并为同一个 `Cookie` 请求头。

## 断言能力

当前断言系统2.0支持：

- `status_code`
- `business_code`
- `json_path`
- `response_time`

JSONPath 读取能力由 `jsonpath-ng` 提供。

统一断言结构：

```json
{
  "id": "string",
  "source": "swagger | ai | user",
  "type": "status_code | json_path | business_code",
  "path": "$.code",
  "operator": "== | != | exists | contains",
  "expected": 200,
  "priority": 1,
  "enabled": true
}
```

融合规则：

- 收集 Swagger、AI、用户三层断言。
- 优先级排序：`user > swagger > ai`。
- 同 path 去重，保留最高优先级。
- AI 断言默认禁用，仅作为建议和追踪信息。
- 最终执行 `final_assertions`。

business_code 规则：

- 不再写死 `business_code = 1`。
- 支持 `success_codes`，例如 `[200, 0]`。
- 支持 `success_expression`，例如 `$.code == 200`。
- `$.data` 相关断言仅在业务成功后执行。

DSL 规则：

- 用户断言使用 DSL 保存，例如 `$.code == 200`、`$.data != null`、`status_code == 200`。
- 执行引擎收集 DSL 后，通过 `backend/app/core/assertion_dsl.py` 转换为内部结构化断言。
- AI 生成断言保存为 `test_case.dsl_assertions`，并同步为 `test_case.assertions` 供执行层使用。
- Swagger 基础断言展示为 DSL，执行前转换为内部结构。
- JSON 断言结构只在执行层和兼容逻辑中使用，不作为用户编辑语言。

第 10 阶段执行结果保存增强：

- `response_data` 保存 JSON 响应；非 JSON 响应保存原始文本、Content-Type 和 JSON 解析错误提示。
- `assertion_result` 保存每条断言的通过状态和失败原因。
- 不在报告或日志中输出完整 token / cookie。

- `assertion_result.final_assertions` 保存最终融合断言。
- 每条断言保留 `source`，可追踪来源为 `ai`、`swagger` 或 `user`。
- 被禁用的 AI 建议会标记为 skipped，不参与最终 pass/fail。

## 第 11 阶段输入兼容

第 11 阶段真实 AI 生成的测试用例不改变 execution_engine 的执行流程。

AI 生成结果当前先输出 `test_strategy` 测试策略结构，并按 Coverage Engine 映射到 7 类测试维度。后端校验通过后再标准化为 `TestCaseUnifiedModel v1`：

- `test_case.request_data`：保存 `method`、`path`、`headers`、`query`、`path_params`、`body`。
- `test_case.dsl_assertions`：保存 AI 生成的 DSL 断言。
- `test_case.assertions`：保存由 DSL 转换得到的内部结构化断言。
- `test_case.coverage_tag`：保存覆盖维度。
- `test_case.priority` / `risk_level`：保存优先级和风险等级。
- `test_case.ai_metadata`：保存测试目的、设计原因、AI 供应商、模型和生成模式。

执行时仍由 `PytestProjectGenerator` 读取 `test_case`，融合 Swagger、AI、用户断言，并生成 Pytest + Requests 工程。历史 `steps` / `variables` 字段仅作为旧数据迁移兼容入口，不作为当前主模型。

本阶段没有修改：

- `POST /api/v1/executions/run`
- `execution_task`
- `execution_result`
- `test_report`
- Pytest 模板目录

## 执行稳定性与错误兜底

当前 `POST /api/v1/executions/run` 已加入执行稳定性兜底。执行过程中的请求、响应、断言、pytest 调用和结果读取均需要被安全处理：

- 生成 Pytest 工程或执行 pytest 失败时，任务状态写为 `failed`，并生成基础日志和报告路径。
- DSL 解析失败、JSONPath 为空、JSONPath 非法、响应非 JSON、断言类型不支持等问题，不允许导致接口层 500，而是写入单条用例的 `assertion_result.items[].message` 或 `error_message`。
- pytest 超时会返回非 0 exit code，并保存到 `execution_task.config.pytest_exit_code`。
- `results.jsonl` 中单行 JSON 损坏时，该行转换为 failed 结果，不影响接口响应。
- 非系统级异常统一转换为 failed 执行结果；数据库不可用等系统级异常仍可能由接口层返回错误。

当前执行流程：

```text
POST /api/v1/executions/run
  -> 创建 execution_task(running)
  -> 生成 storage/generated/project_{project_id}/execution_{task_id}
  -> subprocess 调用 pytest
  -> 读取 results/results.jsonl
  -> 保存 execution_result
  -> 保存 test_report
  -> 更新 execution_task(passed/failed)
```

断言容错规则：

- `final_assertions` 为空时，不执行断言，按请求执行结果继续处理。
- AI 建议断言默认 `enabled=false`，只记录 skipped，不决定 pass/fail。
- `$.data` 相关断言仅在业务成功后执行。
- `business_code` 不再写死为 1，使用 `success_codes` 或 `success_expression`。

## TestCaseUnifiedModel v1 执行输入

当前执行引擎生成 Pytest 工程时优先读取统一测试用例模型：

- `request_data.method` / `request_data.path` 生成请求方法和路径。
- `request_data.headers`、`request_data.query`、`request_data.path_params`、`request_data.body` 生成请求参数。
- `dsl_assertions` 与 `assertions` 参与断言融合。
- `coverage_tag`、`risk_level`、`ai_metadata` 会作为用例上下文写入生成工程，便于后续报告和排查。

历史 `steps` / `variables` 仅作为旧数据兼容输入；新生成和新编辑的测试用例以 `TestCaseUnifiedModel v1` 为准。
