# 后端接口设计

所有接口统一返回：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

## 环境管理

```text
POST   /api/v1/projects/{project_id}/environments
GET    /api/v1/projects/{project_id}/environments
GET    /api/v1/environments/{environment_id}
PUT    /api/v1/environments/{environment_id}
DELETE /api/v1/environments/{environment_id}
```

第 10 阶段未新增环境管理 API 路径，环境鉴权配置复用 `environment.headers` 和 `environment.variables`。

`headers` 用于保存环境公共请求头。`variables` 中约定保存：

- `auth_type`：`none`、`bearer`、`token`、`cookie`、`custom`
- `token`：执行测试时使用的访问令牌
- `cookie`：执行测试时使用的 Cookie
- `auth_config_json`：扩展鉴权配置，可包含 `token_header`、`token_prefix`、`headers` 等
- `timeout_seconds`：环境默认超时时间
- `retry_count`：环境默认重试次数

敏感信息当前存储在环境配置中，仅用于本地 MVP 演示；执行报告和日志不输出完整 token / cookie。

## 接口文档导入

旧导入接口仍保留：

```text
POST /api/v1/projects/{project_id}/api-documents/openapi
POST /api/v1/projects/{project_id}/api-documents/openapi-file
POST /api/v1/projects/{project_id}/api-documents/curl
```

第 9 阶段新增预览和保存接口：

```text
POST /api/v1/projects/{project_id}/documents/preview-url
POST /api/v1/projects/{project_id}/documents/import-url
```

`preview-url` 只解析和筛选，不写入数据库。`import-url` 根据预览结果保存选中接口或保存全部接口。

支持输入类型：

- `auto`
- `online_url`
- `single_api_doc_url`
- `openapi_json_url`
- `openapi_json_text`
- `curl_text`
- `api_path`

请求字段：

- `name`：文档名称
- `input_type`：输入类型，默认 `auto`
- `input_content`：URL、JSON、curl 或接口路径
- `cookie`：可选 Cookie，用于访问需要登录态的 Knife4j / Swagger 文档；不要填写 `Cookie:` 前缀，后端会自动兼容并去掉该前缀
- `api_path_filter`：接口路径筛选
- `method_filter`：请求方法筛选，支持 GET、POST、PUT、DELETE、PATCH
- `keyword_filter`：接口名称、summary、description、operationId、tag、path 关键词筛选
- `group_filter`：接口分组筛选
- `need_ai_parse`：是否启用 mock AI 辅助提示

`import-url` 额外支持：

- `save_mode`：`save_selected` 或 `save_all`
- `selected_endpoint_keys`：选中接口 key
- `endpoints`：前端编辑确认后的接口预览数据

导入规则：

- 有结构化 OpenAPI/Swagger 文档时优先结构化解析。
- `doc.html`、`swagger-ui.html`、`swagger-ui/index.html` 会尝试发现真实 JSON 文档。
- `/swagger-resources` 会尝试读取分组并继续发现真实接口文档。
- 如果提供 `cookie`，后端访问 `doc.html`、`/v3/api-docs`、`/v3/api-docs/{group}`、`/v2/api-docs`、`/v2/api-docs?group={group}`、`/swagger-resources`、`/api-docs`、`/openapi.json`、`/swagger.json` 时都会携带该 Cookie。
- 单接口文档页面 URL 只使用 `#` 后内容作为筛选 hint。
- 只有接口路径且找不到已有资产时，只允许保存待完善接口草稿。
- AI 只做 mock 辅助提示，不凭空编造参数并直接保存。
- Cookie 只在本次请求中使用，默认不保存到 `api_document`、`api_endpoint` 或日志，也不会在接口响应中返回。
- 当前不支持自动登录、验证码、SSO、登录页跳转或浏览器自动化登录。
- 如果仍返回 401/403，表示当前接口文档需要登录态，请确认 Cookie 是否正确、是否过期，并确认 Cookie 属于对应文档系统。
- OpenAPI / Swagger 解析支持基础 `$ref` 展开，优先解析 `components.schemas` / `definitions` 中的模型引用。
- 参数会区分 `query`、`path`、`header`、`cookie`，并尽量保留 `required`、`type`、`description`、`example`、`default`、`schema` 和可执行 `value`。
- Body JSON 优先使用文档 `example / examples`，没有示例时根据展开后的 schema 生成可编辑草稿。
- 响应 JSON 按 status code 解析，优先使用 response examples，没有示例时根据展开后的 schema 生成响应示例。
- 展开后的 schema、原始 schema 和示例数据复用 `request_params`、`request_body_schema`、`response_schema`、`example_request`、`example_response` 等现有 JSON 字段保存，不新增数据库字段。
- 前端第 3 步会基于上述返回字段适配出 `params_example_json`、`params_schema_json`、`params_edit_json`、`body_example_json`、`body_schema_json`、`body_edit_json`、`response_example_json`、`response_schema_json`、`response_edit_json`。
- 保存接口资产时，用户编辑后的示例 JSON 优先写入 `example_request` / `example_response`，Schema 结构继续写入 `request_params`、`request_body_schema`、`response_schema`。
- Schema 展开用于查看完整字段结构，不会因为用户切换展示模式而自动覆盖可执行请求 JSON。

## Pytest + Requests 执行

```text
POST /api/v1/executions/run
```

执行结果写入：

- `execution_task`
- `execution_result`
- `test_report`

执行接口返回值包含：

- `task`：执行任务信息。
- `results`：单条用例执行结果列表，包含 `request_data`、`response_data`、`status_code`、`response_time_ms`、`assertion_result` 和 `error_message`。
- `report`：测试报告元信息。
- `generated_project_path`、`report_path`、`log_path`：生成工程、报告和日志路径。

第 10 阶段执行增强：

- 执行时读取环境公共 headers 和鉴权配置。
- 请求头合并优先级为：环境公共 headers < 环境鉴权 headers < 测试用例请求 headers。
- 支持 `bearer` / `token` / `cookie` / `custom` 类型的基础鉴权配置。
- 支持环境默认 `timeout_seconds` 和 `retry_count`。
- `request_data` 保存脱敏后的有效请求数据，并包含脱敏 curl 命令。
- `response_data` 优先保存 JSON；如果响应不是 JSON，则保存 `raw_text`、`content_type` 和 `json_parse_error`。
- `assertion_result` 保存每条断言的通过状态和失败原因。
- 报告与日志中不输出完整 token / cookie。

业务断言能力：

- `status_code`
- `business_code`
- `business_success`
- `json_path_equal`
- `json_path_not_null`
- `json_path_not_empty`
- `json_path_contains`
- `response_time`

当响应 JSON 中存在 `code` 或 `success` 且测试用例没有显式断言这些路径时，执行引擎会自动补充默认业务断言，避免 HTTP 200 但业务失败仍被判定为通过。

前端执行报告页基于 `results.request_data`、`results.response_data` 和 `results.assertion_result` 展开显示请求参数 JSON、响应体 JSON、curl 命令和断言结果。不新增后端 API。

生成路径：

- 测试工程：`storage/generated/project_{project_id}/execution_{task_id}/`
- 报告：`storage/reports/execution_{task_id}/report.html`
- 日志：`storage/logs/execution_{task_id}/pytest.log`
