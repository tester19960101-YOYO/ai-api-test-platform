## 断言 DSL

```text
POST /api/v1/assertion/parse
POST /api/v1/assertion/to-dsl
```

兼容别名：

```text
POST /api/assertion/parse
POST /api/assertion/to-dsl
```

`parse` 入参：

```json
{
  "dsl": "$.code == 200"
}
```

返回结构化断言 JSON，供后端执行层使用。

`to-dsl` 入参：

```json
{
  "assertion": {
    "type": "json_path",
    "path": "$.msg",
    "operator": "contains",
    "expected": "成功"
  }
}
```

返回 DSL 字符串。

支持操作：

```text
==  !=  >  <  contains  exists  not null
```

## 接口文档导入

旧导入接口仍保留：

```text
POST /api/v1/projects/{project_id}/api-documents/openapi
POST /api/v1/projects/{project_id}/api-documents/openapi-file
POST /api/v1/projects/{project_id}/api-documents/curl
```

第 9 阶段新增预览和保存接口：

```text
POST /api/v1/projects/{project_id}/documents/preview-url
POST /api/v1/projects/{project_id}/documents/import-url
```

`preview-url` 只解析和筛选，不写入数据库。`import-url` 根据预览结果保存选中接口或保存全部接口。

支持输入类型：

- `auto`
- `online_url`
- `single_api_doc_url`
- `openapi_json_url`
- `openapi_json_text`
- `curl_text`
- `api_path`

请求字段：

- `name`：文档名称
- `input_type`：输入类型，默认 `auto`
- `input_content`：URL、JSON、curl 或接口路径
- `cookie`：可选 Cookie，用于访问需要登录态的 Knife4j / Swagger 文档；不要填写 `Cookie:` 前缀，后端会自动兼容并去掉该前缀
- `api_path_filter`：接口路径筛选
- `method_filter`：请求方法筛选，支持 GET、POST、PUT、DELETE、PATCH
- `keyword_filter`：接口名称、summary、description、operationId、tag、path 关键词筛选
- `group_filter`：接口分组筛选
- `need_ai_parse`：是否启用 AI 辅助提示

`import-url` 额外支持：

- `save_mode`：`save_selected` 或 `save_all`
- `selected_endpoint_keys`：选中接口 key
- `endpoints`：前端编辑确认后的接口预览数据

导入规则：

- 有结构化 OpenAPI/Swagger 文档时优先结构化解析。
- `doc.html`、`swagger-ui.html`、`swagger-ui/index.html` 会尝试发现真实 JSON 文档。
- `/swagger-resources` 会尝试读取分组并继续发现真实接口文档。
- 如果提供 `cookie`，后端访问 `doc.html`、`/v3/api-docs`、`/v3/api-docs/{group}`、`/v2/api-docs`、`/v2/api-docs?group={group}`、`/swagger-resources`、`/api-docs`、`/openapi.json`、`/swagger.json` 时都会携带该 Cookie。
- 单接口文档页面 URL 只使用 `#` 后内容作为筛选 hint。
- 只有接口路径且找不到已有资产时，只允许保存待完善接口草稿。
- AI 只做 mock 辅助提示，不凭空编造参数并直接保存。
- Cookie 只在本次请求中使用，默认不保存到 `api_document`、`api_endpoint` 或日志，也不会在接口响应中返回。
- 当前不支持自动登录、验证码、SSO、登录页跳转或浏览器自动化登录。
- 如果仍返回 401/403，表示当前接口文档需要登录态，请确认 Cookie 是否正确、是否过期，并确认 Cookie 属于对应文档系统。
- OpenAPI / Swagger 解析支持基础 `$ref` 展开，优先解析 `components.schemas` / `definitions` 中的模型引用。
- 参数会区分 `query`、`path`、`header`、`cookie`，并尽量保留 `required`、`type`、`description`、`example`、`default`、`schema` 和可执行 `value`。
- Body JSON 优先使用文档 `example / examples`，没有示例时根据展开后的 schema 生成可编辑草稿。
- 响应 JSON 按 status code 解析，优先使用 response examples，没有示例时根据展开后的 schema 生成响应示例。
- 展开后的 schema、原始 schema 和示例数据复用 `request_params`、`request_body_schema`、`response_schema`、`example_request`、`example_response` 等现有 JSON 字段保存，不新增数据库字段。
- 前端第 3 步会基于上述返回字段适配出 `params_example_json`、`params_schema_json`、`params_edit_json`、`body_example_json`、`body_schema_json`、`body_edit_json`、`response_example_json`、`response_schema_json`、`response_edit_json`。
- 保存接口资产时，用户编辑后的示例 JSON 优先写入 `example_request` / `example_response`，Schema 结构继续写入 `request_params`、`request_body_schema`、`response_schema`。
- Schema 展开用于查看完整字段结构，不会因为用户切换展示模式而自动覆盖可执行请求 JSON。

## AI 用例生成

```text
POST /api/v1/endpoints/{endpoint_id}/testcases/generate
```

第 11 阶段起，该接口调用真实大模型生成可执行测试用例。生成结果保存到 `test_case`，调用记录保存到 `ai_analysis_record`。未配置 AI_API_KEY 时返回 400 配置错误。

当前请求体为空，后端根据 `endpoint_id` 读取已保存的 `api_endpoint`，构造结构化 Swagger/OpenAPI 输入模型后调用真实 AI。

AI 期望输出：

```json
{
  "test_strategy": {
    "normal": [],
    "error": [],
    "boundary": [],
    "security": []
  }
}
```

`test_strategy` 中每条用例必须包含 `name`、`purpose`、`request`、`assertions`、`risk_level`、`reason`。后端会将其标准化为接口响应中的 `test_cases` 列表。

第11阶段新增 Test Coverage Engine 1.0 后，每条用例还必须包含 `coverage_dimension`，取值为：

```text
functional | validation | boundary | negative | security | business | dependency
```

接口响应会返回 `coverage_matrix` 和 `coverage_summary`，用于展示本次生成是否覆盖完整测试维度。

后端会将 AI 输出标准化为 `TestCaseUnifiedModel v1`：

- `test_case.request_data`：保存可执行请求。
- `test_case.assertions`：保存内部结构化断言。
- `test_case.dsl_assertions`：保存用户侧可编辑 DSL 断言。
- `test_case.coverage_tag`：保存覆盖维度标签。
- `test_case.ai_metadata`：保存 AI 供应商、模型、生成模式、测试目的和设计原因等元数据。

## Pytest + Requests 执行

```text
POST /api/v1/executions/run
```

执行结果写入：

- `execution_task`
- `execution_result`
- `test_report`

执行接口返回值包含：

- `task`：执行任务信息。
- `results`：单条用例执行结果列表，包含 `request_data`、`response_data`、`status_code`、`response_time_ms`、`assertion_result` 和 `error_message`。
- `report`：测试报告元信息。
- `generated_project_path`、`report_path`、`log_path`：生成工程、报告和日志路径。

第 10 阶段执行增强：

- 执行时读取环境公共 headers 和鉴权配置。
- 请求头合并优先级为：环境公共 headers < 环境鉴权 headers < 测试用例请求 headers。
- 支持 `bearer` / `token` / `cookie` / `custom` 类型的基础鉴权配置。
- 支持环境默认 `timeout_seconds` 和 `retry_count`。
- `request_data` 保存脱敏后的有效请求数据，并包含脱敏 curl 命令。
- `response_data` 优先保存 JSON；如果响应不是 JSON，则保存 `raw_text`、`content_type` 和 `json_parse_error`。
- `assertion_result` 保存每条断言的通过状态和失败原因。
- 报告与日志中不输出完整 token / cookie。

业务断言能力：

- `status_code`
- `business_code`
- `business_success`
- `json_path_equal`
- `json_path_not_null`
- `json_path_not_empty`
- `json_path_contains`
- `response_time`

当响应 JSON 中存在 `code` 或 `success` 且测试用例没有显式断言这些路径时，执行引擎会自动补充默认业务断言，避免 HTTP 200 但业务失败仍被判定为通过。

第 10.1 阶段断言系统2.0：

- 新增核心模块：`backend/app/core/assertion_engine_v2.py`。
- Swagger/OpenAPI 断言作为基础层，来源为 `swagger`。
- AI mock 断言作为建议层，来源为 `ai`，默认不控制 pass/fail。
- 用户断言作为最高优先级，来源为 `user`。
- 融合顺序为 `user > swagger > ai`。
- 同 path 断言去重，保留最高优先级。
- `business_code` 支持 `success_codes` 和 `success_expression`，不再写死 1。
- `$.data` 相关断言仅在业务成功后执行。
- `assertion_result` 中保留最终断言和每条断言来源。
- 第 10.1 阶段后执行引擎优先收集 DSL 断言，执行前转换为内部结构化断言。
- AI 断言保存为 `test_case.dsl_assertions`，并同步生成 `test_case.assertions` 供执行层使用；前端仍以 DSL 作为用户编辑语言。

前端执行报告页基于 `results.request_data`、`results.response_data` 和 `results.assertion_result` 展开显示请求参数 JSON、响应体 JSON、curl 命令和断言结果。不新增后端 API。

生成路径：

- 测试工程：`storage/generated/project_{project_id}/execution_{task_id}/`
- 报告：`storage/reports/execution_{task_id}/report.html`
- 日志：`storage/logs/execution_{task_id}/pytest.log`

## 执行接口错误处理补充

`POST /api/v1/executions/run` 当前对执行链路增加容错处理。除数据库连接不可用等系统级异常外，执行过程中的 DSL 解析失败、JSONPath 非法、响应 JSON 解析失败、pytest 超时或结果文件坏行，均应返回统一响应格式，任务和用例结果状态为 `failed`，不应直接返回 HTTP 500。

失败信息保存位置：

- `execution_task.status = failed`
- `execution_result.status = failed`
- `execution_result.error_message` 保存失败原因
- `execution_result.assertion_result` 保存断言执行明细
- `test_report.status = failed` 或报告元信息保存失败摘要
- `storage/logs/execution_{task_id}/pytest.log` 保存执行日志

该修复不新增 API，不修改数据库结构，不改变接口导入、AI mock 用例生成和鉴权配置流程。
## 第11阶段专项修复：AI 用例生成接口真实 OpenAI 调用

接口路径保持不变：

```text
POST /api/v1/endpoints/{endpoint_id}/testcases/generate
```

当前调用链：

```text
POST /api/v1/endpoints/{endpoint_id}/testcases/generate
  -> 根据 endpoint_id 查询 api_endpoint
  -> 构建 Swagger/OpenAPI 结构化接口模型
  -> CoverageEngine 生成 coverage_matrix
  -> 通过 LLMFactory 调用 OpenAIClient 或 QwenClient
  -> 校验模型返回的 test_strategy JSON
  -> 校验 coverage_dimension 是否覆盖完整
  -> 标准化为可执行 test_case 结构
  -> 保存到 test_case
  -> 保存 ai_analysis_record
```

错误处理：

- `AI_API_KEY` 缺失时返回 400，提示 `AI_API_KEY 未配置，无法调用真实 OpenAI`。
- OpenAI 调用失败、返回非 JSON、结构不合法时返回可控错误，不保存半成品测试用例。
- 运行时不再静默 fallback 到 mock/fake LLM。
- mock/fake LLM 仅用于单元测试。

AI 输出断言必须是 DSL 字符串数组，例如：

```json
{
  "assertions": ["status_code == 200", "$.code == 200"]
}
```

本次专项修复不修改 execution_engine，不新增数据库表，不改变现有 API 入参结构。

## AI 多模型配置

`POST /api/v1/endpoints/{endpoint_id}/testcases/generate` 接口路径和入参不变，但底层 AI 调用通过 `LLMFactory` 按配置切换模型：

```text
AI_PROVIDER=openai
AI_API_BASE_URL=https://api.openai.com/v1
AI_MODEL_NAME=gpt-4o-mini
```

```text
AI_PROVIDER=qwen
AI_API_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
AI_MODEL_NAME=qwen-max-latest
```

Qwen 分支不使用 OpenAI 的 `response_format` 参数，后端统一对返回文本做 JSON 解析和结构校验。模型返回非 JSON 或结构不合法时，接口返回可控错误并且不写入半成品测试用例。
## AI 用例生成接口稳定性说明

`POST /api/v1/endpoints/{endpoint_id}/testcases/generate` 当前返回结构中包含：

- `test_cases`：已保存的测试用例列表。
- `coverage_matrix`：本次要求覆盖的测试维度矩阵。
- `coverage_summary`：本次生成后各维度用例数量和缺失维度。

真实模型返回的 DSL 断言会在入库前解析校验。无法解析的 DSL 字符串不会导致接口返回 500；后端会忽略非法 DSL，并按 `coverage_dimension` 使用默认断言补齐。对象断言、空断言、`business_code == 1` 仍视为非法输出，不会作为有效断言保存。

## TestCaseUnifiedModel v1 接口返回

测试用例相关接口当前返回统一结构：

```text
POST /api/v1/testcases
GET  /api/v1/testcases
GET  /api/v1/projects/{project_id}/testcases
GET  /api/v1/testcases/{test_case_id}
PUT  /api/v1/testcases/{test_case_id}
```

同时保留历史路径 `/api/v1/test-cases` 作为兼容入口。

统一返回字段包括：

- `endpoint`：接口 ID、名称、方法和路径。
- `type`：7 类覆盖维度。
- `priority`：`P0`、`P1`、`P2`。
- `status`：`generated`、`edited`、`disabled`、`passed`、`failed`。
- `request` / `request_data`：统一请求结构。
- `assertions`：内部结构化断言。
- `dsl_assertions`：前端展示和编辑的 DSL。
- `coverage_tag`、`risk_level`、`data_dependency`、`ai_metadata`。

`PUT /api/v1/testcases/{test_case_id}` 支持更新 `assertions`、`dsl_assertions`、`type`、`priority`、`request`、`coverage_tag`、`risk_level` 等统一模型字段。

## 测试用例接口兼容修复

当前测试用例接口同时支持横杠路径和无横杠路径，便于前端页面和历史调用兼容：

- `GET /api/v1/projects/{project_id}/test-cases`
- `GET /api/v1/projects/{project_id}/testcases`
- `GET /api/v1/testcases?project_id={project_id}`
- `PUT /api/v1/test-cases/{test_case_id}`
- `PUT /api/v1/testcases/{test_case_id}`

后端读取历史测试用例时会将 `steps` / `variables` 兼容转换为 `TestCaseUnifiedModel v1` 字段，包括 `request`、`dsl_assertions`、`coverage_tag`、`risk_level`、`ai_metadata`。因此前端测试用例列表、AI 用例生成页编辑抽屉和执行报告页可以读取同一结构。

接口导入预览接口遇到目标文档 401/403 时仍返回统一响应格式，并在 `warnings` / `errors` 中提示 Cookie 登录态问题；该情况表示目标 Knife4j / Swagger 服务拒绝访问，不表示平台接口 404。
